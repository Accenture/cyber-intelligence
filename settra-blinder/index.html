Technical analysis

Settra Blinder demonstrates sophisticated kernel-level attack capabilities across several technique categories:

BYOVD — Bring Your Own Vulnerable Driver: Exploits legitimately signed but vulnerable drivers to gain kernel read/write primitives. Known targeted drivers include RTCore64.sys (CVE-2019-18093) and AsrDrv101.sys (CVE-2020-12446).
TechniqueDescription
BYOVD Exploitation Loads vulnerable signed drivers (RTCore64.sys, AsrDrv101.sys) to gain kernel memory access without triggering DSE
Direct Syscall Invocation Bypasses user-mode API hooks by invoking syscalls directly, evading EDR instrumentation at the API layer
PPL Bypass Circumvents Process Protection Level controls to access and manipulate protected security processes
Ps Callback Enumeration Enumerates and disables PsSetCreateProcessNotifyRoutine, PsSetCreateThreadNotifyRoutine, and PsSetLoadImageNotifyRoutineEx kernel callbacks used by EDR sensors
ETW-TI Patching Patches Event Tracing for Windows Threat Intelligence providers via direct memory manipulation, blinding kernel telemetry collection
AMSI Patching Disables the Antimalware Scan Interface through in-memory patching, preventing script and content scanning
PPID Spoofing Spoofs process parent IDs to simulate creation from legitimate system processes such as explorer.exe
03

Mitigation

APEX Labs recommends the following measures to mitigate the risk posed by Settra Blinder:

  • Implement and maintain updated kernel patches to prevent exploitation of known vulnerable drivers.
  • Deploy Driver Signature Enforcement (DSE) and Secure Boot to prevent unsigned or vulnerable driver loading.
  • Implement strict access controls to prevent unauthorized access to kernel interfaces and system management functions.
  • Keep operating system and kernel patches updated to mitigate vulnerabilities that could be exploited via BYOVD techniques.
  • Enable system logging including kernel-level events, driver activities, and security configuration changes to support detection and forensic investigation.

YARA rule

The following YARA rule detects Settra Blinder based on CLI argument strings, vulnerable driver device paths, kernel callback routine names, and runtime log strings. Security teams are encouraged to deploy this rule across endpoint and file-scanning solutions.

settra_blinder.yar
Windows x64 10 Jul 2026 
rule settra_blinder
{
  meta:
    description = "Detects EDR Blinder"
    author      = "Accenture Cyber Intelligence"
    date        = "2026-07-10"
    hash        = "32d6657506d861c206a5c47c62bba4c82231d4a12f12d258908a46f7e5f637bc"

  strings:
    // CLI argument strings
    $args1 = "--asrdrv" ascii wide
    $args2 = "--ppid" ascii wide
    $args3 = "--kill-loop" ascii wide
    $args4 = "--stpm" ascii wide

    // Vulnerable driver device paths (BYOVD targets)
    $drvdev1 = "\\\\.\\RTCore64" ascii wide
    $drvdev2 = "\\\\.\\AsrDrv101" ascii wide
    $drvdev3 = "\\\\.\\gdrv" ascii wide
    $drvdev4 = "\\\\.\\HpPortIox64" ascii wide
    $drvdev5 = "\\\\.\\PhysMem" ascii wide
    $drvdev6 = "\\\\.\\WinRing0_1_2_0" ascii wide
    $drvdev7 = "\\\\.\\STProcessMonitorDriver" ascii wide

    // Kernel callback routine names
    $krlstruct1 = "PsSetCreateProcessNotifyRoutine" ascii wide
    $krlstruct2 = "PsSetCreateThreadNotifyRoutine" ascii wide
    $krlstruct3 = "PsSetLoadImageNotifyRoutineEx" ascii wide
    $krlstruct4 = "PsSetLoadImageNotifyRoutine" ascii wide
    $krlstruct5 = "PsCreateProcess" ascii wide
    $krlstruct6 = "PsCreateThread" ascii wide
    $krlstruct7 = "PsLoadImage" ascii wide
    $krlstruct8 = "ObProcess" ascii wide
    $krlstruct9 = "ObThread" ascii wide

    // Runtime log strings
    $log1 = "[*] === ETW Threat Intelligence Provider Bypass ===" ascii wide
    $log2 = "[*] === PPL Bypass ===" ascii wide
    $log3 = "[*] === ETW + AMSI self-patch ===" ascii wide
    $log4 = "[*] === Minifilter Scan ===" ascii wide

  condition:
    3 of ($args*) and 4 of ($drvdev*) and 5 of ($krlstruct*) and 2 of ($log*)
}

The condition requires a minimum threshold across all four string groups — reducing false positives while tolerating minor sample variation. Any binary matching 3+ CLI args, 4+ driver paths, 5+ kernel callback names, and 2+ log strings is a high-confidence match.
