Network Fingerprints

📅 March 2026 🏷 Accenture Security ATHENA

RustyRocket's TLS stack produces consistent fingerprints that can be used to identify C2 traffic at the network layer, even when the payload is encrypted. Deploy these in your IDS/NSM tooling alongside the SNI-based indicators.

SNI Indicators

Alert on TLS ClientHello packets containing any of the following invalid or suspicious SNI values known to be used by RustyRocket during the C2 handshake: 

"server"
"router"
"proxy"

These are not legitimate domain names and will not appear in normal TLS traffic. Any match should be treated as a high-confidence indicator of compromise.

TLS-within-TLS Tunnelling

RustyRocket proxies are capable of nesting TLS connections inside an outer TLS session. Where your network security tooling supports TLS inspection, enable it and alert on:

  • Unexpected WebSocket upgrade requests inside HTTPS sessions
  • TLS handshakes appearing inside already-decrypted HTTPS streams
  • Anomalous session volumes to low-reputation or newly-registered domains
Detection note: The proxy's Rust TLS stack emits distinctive error strings (tls handshake eof, unexpected polling after handshake, JoinError::Cancelled() that may appear in debug logs or be recoverable from memory. These are also targeted by the Windows Proxy YARA rule.

Deploying Fingerprints

Both JA4 and JA3 fingerprints can be used directly in common NSM platforms:

  • Zeek: Add the fingerprint to your ja3 or ja4 Intel feeds.
  • Suricata: Use ja3.hash or ja4 keyword in rules.
  • SIEM: Index tls.ja3 / tls.ja4 fields and create threshold alerts.
